## F1 - HIGH: Shell-injection via `exec` in briefer.ts

**File:** `packages/engine/src/briefer.ts:146`

**What goes wrong:**
`callBob` builds a command string and passes it to `exec()`, which invokes a
shell. Although the static parts of the string are literals, `config.bobMaxCost`
is read from environment config and coerced with `Number()`. If an attacker
controls the environment (or a config file) and injects shell metacharacters
before `Number()` receives the value, the coercion returns `NaN` and the
string `NaN` ends up in the shell command, which is harmless today but only
by accident. More importantly, using a shell at all is unnecessary and risky -
if the command string is ever extended to include any user-supplied string
(e.g. a model ID, a mode slug), injection becomes exploitable.

**Suggested fix:**
Replace `exec` with `execFile` (or `spawn`), passing arguments as an array.
This eliminates the shell entirely. The `--max-cost` value should be validated
as a positive number before use, and the `--mode` slug should be validated
against an allowlist before being passed.

## F2 - HIGH: Unbounded in-memory event history in server.ts

**File:** `packages/engine/src/server.ts:209-213`

**What goes wrong:**
`forge.history` is a plain array that grows without limit for the lifetime of
the server process. A long forge run (40 commits * 3 fail runs + pass run each)
can produce hundreds of events. Each subsequent SSE client that connects
replays the entire history from memory. With large `output` strings in briefed
events, this can grow into tens of megabytes and is never freed. A single forge
run also never clears history between pipeline retries within the same process.

**Suggested fix:**
Cap `forge.history` at a fixed length (e.g. 2000 entries), dropping the oldest
event when the cap is exceeded. Alternatively, persist the history to a temp
file and stream it from there; this also survives server restarts.

## F3 - HIGH: Race condition on `next` counter in parallel forge workers

**File:** `packages/engine/src/forge.ts:159-161`
**Also:** `packages/engine/src/certifier.ts:368-370`

**What goes wrong:**
Both `runBrief` and `certify` use a shared mutable `next` counter that is
incremented with `next++` inside async workers. In Node.js, integer increment
is not interrupted by the event loop, so there is no data race for the
increment itself. However, after the increment the current slot reads
`queue[next++]` - if `next` was already equal to `queue.length` when another
worker just incremented it to `queue.length + 1`, the outer `while` guard
can still be true for the first worker at the start of its iteration, leading
it to read `candidates[idx]` as `undefined`. The `!` non-null assertion on
line 370 of `certifier.ts` suppresses the TypeScript error but does not prevent
the runtime `undefined` dereference.

**Suggested fix:**
Capture the index and guard atomically:
```ts
const idx = next;
if (idx >= candidates.length) break;
next++;
const candidate = candidates[idx]!;
```
Both loops already have `while (next < ...)` but the index is read after the
increment, not before, so the guard and the read can diverge under re-entrance
if the queue is exhausted exactly as a slot starts its loop body.

## F4 - MEDIUM: Worktree name collision for concurrent runs on the same SHA

**File:** `packages/engine/src/certifier.ts:85`

**What goes wrong:**
The temporary worktree path is `os.tmpdir()/dejabug-wt-<fixSha>`. When two
certify calls are started with the same candidate SHA (e.g. via `--redo`), they
both compute the same path. The second call's `addWorktree` will `rm -rf` the
directory the first call is actively using, corrupting the first run silently.

**Suggested fix:**
Include a unique element in the path, e.g. `dejabug-wt-${fixSha}-${slot}-${Date.now()}`,
or use `crypto.randomBytes`. The playground export in `play.ts:85` already
uses `process.pid` for this purpose - apply the same pattern here.

## F5 - MEDIUM: `state.json` parsed without schema validation in server.ts

**File:** `packages/engine/src/server.ts:48-50`

**What goes wrong:**
On startup the server reads `.dejabug/state.json` and casts it directly to
`State` with `as State`. If the file was written by an older version of the
engine (or is manually edited and malformed), fields like `sessions` could be
missing, null, or of the wrong type. Any subsequent access to
`state.sessions[key]` will throw a runtime TypeError that crashes request
handlers and is never caught.

**Suggested fix:**
Validate the parsed object before trusting it. At minimum:
```ts
const raw = JSON.parse(readFileSync(stateFile, "utf8"));
const state: State = {
  sessions: (raw?.sessions && typeof raw.sessions === "object") ? raw.sessions : {},
  profile: raw?.profile,
};
```
A Zod schema for `State` is more robust.

## F6 - MEDIUM: Unhandled rejection in fire-and-forget forge pipeline

**File:** `packages/engine/src/server.ts:231-247`

**What goes wrong:**
The forge pipeline is started with `void (async () => { ... })()`. The inner
`runForge` call is awaited and `runForge` itself has a top-level try/finally
that emits `done`, so normal errors are handled. However `initRepo` on
line 239 calls `execFileSync("git", ["clone", ...])`. If the process is
killed mid-clone, or the workspace disk fills up, `initRepo` can throw even
after the `try/catch` on line 238-244 logs the clone failure - for example,
if `detectAdapter` itself throws. Any unhandled rejection from this block is
silently swallowed by `void`, leaving `forge.running = true` permanently and
the server stuck refusing new forge requests with a 409.

**Suggested fix:**
Wrap the entire fire-and-forget block in a try/finally that always emits
`{ type: "done" }` and resets `forge.running = false`, regardless of how
`initRepo` or `runForge` exits.

## F7 - MEDIUM: Path traversal in `readCase` partially blocked but inconsistently applied

**File:** `packages/engine/src/store.ts:124-127`
**Also:** `packages/engine/src/server.ts:68-71`

**What goes wrong:**
`readCase` guards the `id` parameter against path traversal with a hex-SHA
regex (`/^[0-9a-f]{7,40}$/`). This is correct. However `repoConfig` in
`server.ts:60-66` constructs a `casesDir` from the query parameter `repo`
after validating it against `REPO_NAME = /^[A-Za-z0-9_.-]+$/`. The pattern
allows `.` which means `repo=..` passes the regex (two dots). An attacker
supplying `?repo=..` would cause `path.join(casesRoot, "..")` to resolve to
the parent of `cases/`, exposing unintended directories to `readCases` and
`readCandidates`.

**Suggested fix:**
Reject any `repo` value that contains a dot or that equals `..` explicitly:
```ts
if (!REPO_NAME.test(name) || name.includes("."))
  throw new HttpError(400, "invalid repo name");
```

## F8 - LOW: `writeJsonAtomic` temp file survives process crash

**File:** `packages/engine/src/store.ts:32-37`

**What goes wrong:**
The temp file is named `${file}.${process.pid}.tmp`. On a normal run the rename
removes it. If the process is killed between `writeFileSync` and `renameSync`,
the `.tmp` file is left on disk and will accumulate silently. On the next
startup no code cleans these up. On Windows, if the target file is held open
(e.g. by an antivirus scan), `renameSync` throws and the tmp file is orphaned.

**Suggested fix:**
At server startup (or before any write), scan for and delete `*.tmp` files
older than a few minutes in the state and cases directories. Alternatively,
use an established atomic-write library that handles the cross-platform edge
cases (e.g. `write-file-atomic`).

## F9 - LOW: `forge.history.forEach(send)` iterates concurrently with push

**File:** `packages/engine/src/server.ts:267-268`

**What goes wrong:**
When a new SSE client connects, the handler replays `forge.history` with
`forEach`, then registers the live listener. Between those two lines, new
events may be pushed by the running pipeline. These events are caught by
the live listener. However, if an event arrives during the `forEach` call
itself, it will be added to the array while iteration is ongoing (JavaScript
array iteration is not snapshot-based), potentially delivering that event
twice (once from the replay, once from the live listener) or missing it
entirely if `forEach` ends before the listener is attached.

**Suggested fix:**
Snapshot the history before attaching the listener:
```ts
const snapshot = forge.history.slice();
forge.emitter.on("forge", send);
snapshot.forEach(send);
```
Registering the listener first and then replaying the snapshot ensures no
event is ever missed. Duplicate delivery of the boundary event is then
possible but innocuous for idempotent rendering.

## F10 - LOW: Insecure direct object reference via `PUT /api/profile`

**File:** `packages/engine/src/server.ts:200-206`

**What goes wrong:**
The profile endpoint accepts and persists arbitrary JSON from any client
without authentication. The only safeguard is a 64 KB size cap. On a
multi-user machine or when the server is accidentally exposed on a non-loopback
interface, any process that can reach the server can overwrite the profile.
The server does bind to `127.0.0.1` (line 281), which limits exposure to
localhost, but the threat remains for shared developer machines or container
setups where loopback is shared.

**Suggested fix:**
For the hackathon scope, document the localhost-only binding as the security
boundary. For production, add a `DEJABUG_API_KEY` environment variable and
require it on mutating endpoints (`PUT /api/profile`, `POST /api/forge`,
`POST /api/cases/:id/start`).
